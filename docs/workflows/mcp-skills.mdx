The MCP server serves a skills pack alongside the tools. A skill is a document
that tells an agent how to do one job well, including the judgement calls the
tools cannot make on their own: what to confirm before launching a scan, how
to record a verdict, when a dependency is safe to add.

The pack is what the agent reads when a request needs more than a tool call.
`create_scan` launches a scan. The `onboarding` skill tells the agent how to
walk a brand-new account through their first one.

## How a client gets the pack

There are two ways a client reaches the pack, and which one it uses depends
on what the client supports.

### The native skills surface

The pack is served over the MCP Skills extension (SEP-2640), so a client has
to ask for it. Declare the extension in the client's capabilities:

```json
{
  "io.modelcontextprotocol/protocolVersion": "2026-07-28",
  "io.modelcontextprotocol/clientCapabilities": {
    "extensions": {
      "io.modelcontextprotocol/skills": {}
    }
  }
}
```

A client that calls `skills/list` or `skills/get` without declaring the
extension gets a 400 naming the capability it is missing.

Every skill lives at a URI under one namespace:

```text
skill://zeroquarry/<skill-name>/SKILL.md
```

The `skills/list` method returns each skill's frontmatter and a manifest of
its files with a SHA-256 digest and a size for each. `skills/get` returns one
skill's entry by its `SKILL.md` URI. The generic resource methods serve the
bytes: `resources/list` enumerates them, `resources/read` returns one, and
`resources/directory/read` lists the direct children of a directory.

A client that verifies digests against the manifest gets a mismatch when the
pack changed between the listing and the read. The server checks the size on
read for the same reason, so a pack that changes under a client surfaces as an
error rather than as silently stale content.

### The fallback tools

A client that has not implemented the Skills extension still reaches the pack,
through two ordinary tools: `list_skills` and `load_skill`.

`list_skills` takes no arguments and returns the pack as metadata — each
skill's name, description, `skill://` URI, and supporting files.
`load_skill` takes a skill name and optionally the path of one of that
skill's advertised files; without the file it returns the `SKILL.md`.

The server advertises these two tools only to clients that did *not* declare
the extension, so the catalog stays small for the clients that do have it.
They stay callable from any client regardless, because a client may be
holding a catalog it cached before the switch.

Both paths return the same pack. The difference is only how the bytes arrive.

### Copying the skills instead

The pack is also a plain set of `SKILL.md` files, so a client that can read
local files can be given them directly — save the skill directories into your
agent's skills folder and point the agent at them. The skills are written to
be read by an agent, and they name the console pages where a human takes an
action, so they work the same way whichever way they arrived.

The copy the server serves is the source of truth: `list_skills` lists every
skill with its URI and manifest, and `load_skill` returns the file to save.
Treat the digests as authoritative and refetch rather than assuming a saved
copy is current.

A copied skill still reaches ZeroQuarry over the MCP server: the skills
describe how to use the tools, they do not replace them.

## The pack

| Skill | Use for |
| --- | --- |
| `zeroquarry` | The entrypoint. Orients the agent and routes it to the right tool or skill. |
| `onboarding` | A brand-new account, and "get started" requests. First scan, tier limits, what to set up next. |
| `sast-basic` | A quick, cheap static pass over a repository — the two basic-pass depths, what each costs, and when it is enough. |
| `security-review` | A full security review of a codebase — a pre-release audit, a compliance-mandated scan, or a re-scan after fixes. |
| `remote-scan` | Testing a live target — a URL, a SaaS API, or a host — including scope, authorization, and authenticated testing. |
| `binary-scan` | Scanning a compiled artifact instead of a repository — firmware, an APK, a JAR, a native library. Upload mechanics and size caps included. |
| `outdated-dependencies` | Whether pinned dependencies carry known vulnerabilities — CVEs in manifests and lockfiles, and actively-exploited packages. |
| `slopsquatting` | Whether a dependency or package is safe to add, and hallucinated-package checks. |
| `security-hygiene` | Secure-coding guidance for the code the agent itself writes. Needs no scan and no connection. |
| `automation` | Recurring scans, CI scanning, and delivery into Slack, Jira, Linear, ServiceNow, or email triage. |
| `rest-api` | Capabilities beyond the MCP tools: report exports, SBOM and VEX downloads, share links, patches and auto-fix pull requests, disclosures, schedules, per-scan LLM usage, and multipart uploads too large for MCP. |

The entrypoint is at `skill://zeroquarry/zeroquarry/SKILL.md`. It is what the
server's own discovery instructions point an agent at, and it is the one to
load first: it verifies the connection, lists what is reachable, and points
at the specialised skill for the task.

The pack is not fixed. Skills are added to it as the product gains the
capability to describe, and an agent should list the pack rather than assume
the table above is complete.

A skill can carry **supporting files** alongside its `SKILL.md` — deep
guidance that would otherwise crowd the entry. The listing advertises each
one by path and size, and the agent asks for it by name when it needs the
depth; the bytes are not served with the listing. The `security-review`
skill carries a severity rubric, and the `remote-scan` skill carries the
authentication options, both under `references/`.

The skills are written to the agent, not to a person. They use the tool names
directly, they name the console pages where a human takes an action, and they
carry the rules the agent is expected to follow without being asked.

## How the pack is served

A few properties matter if you are writing a client or running your own
deployment.

The pack is a directory on the server, one subdirectory per skill, and each
subdirectory has a `SKILL.md` with YAML frontmatter carrying at least a `name`
and a `description`. The directory name and the frontmatter `name` have to
match, and both have to be a valid Agent Skills name: lowercase letters,
digits, and hyphens.

A skill that fails validation is excluded whole and never half-served. Either
it is in the listing with its complete manifest, or it is not there at all.
The server logs the reason at startup.

Reads resolve only through the advertised manifest, so a file the listing
does not mention is not served even if it exists on disk. The skill directory
is the containment boundary.

The listing pages at 50 entries. The freshness hint on a read is five
minutes, which only trims how often a host refetches; the pack itself only
changes on deploy.

## Where the pack comes from

The skills are the same documents the product maintains in its own repository,
and they change with the product. A client that cached the pack should treat
the digests as authoritative and refetch rather than assume a skill is
unchanged.

Two of the skills cross into the REST API on purpose. `rest-api` exists
because the MCP tools cover the core loop (launch a scan, poll it, read the
findings) and not the whole surface, and it is the right place to send an
agent that wants a PDF report, an SBOM, or a multipart upload of an artifact
that does not fit through a tool argument.
